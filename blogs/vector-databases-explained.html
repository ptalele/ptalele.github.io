Vector Databases Explained: The Backbone of Modern AI Search

December 29, 2024 · AI · 6 min read

Every RAG pipeline, semantic search feature, and recommendation engine relies on the same underlying primitive: finding the "closest" items in high-dimensional space. Vector databases make this fast at scale, and understanding how they work is essential for anyone building AI-powered products.

From Text to Vectors

Embedding models transform text, images, or other data into dense numerical vectors — typically 384 to 1536 dimensions — where semantic similarity corresponds to spatial proximity. "Dog" and "puppy" end up close together; "dog" and "spreadsheet" end up far apart.

The Core Problem: Approximate Nearest Neighbor Search

Finding the exact nearest vector among millions is computationally expensive at query time. Vector databases use Approximate Nearest Neighbor (ANN) algorithms to trade a small amount of accuracy for massive speed gains:

  • HNSW (Hierarchical Navigable Small World) — builds a multi-layer graph for fast traversal. The most widely used algorithm today (Pinecone, Weaviate, Qdrant).
  • IVF (Inverted File Index) — clusters vectors, then searches only relevant clusters. Used in FAISS.
  • Product Quantization — compresses vectors to reduce memory footprint at the cost of some precision.

Choosing a Vector Database

  • Pinecone — fully managed, easy to start, strong for teams that don't want to manage infrastructure.
  • Weaviate / Qdrant — open-source, self-hostable, rich filtering capabilities alongside vector search.
  • pgvector — adds vector search to PostgreSQL. Ideal if you already run Postgres and want to avoid a new system.
  • FAISS — a library, not a database. Best for embedding directly into an application without a separate service.

Hybrid Search: The Production Reality

Pure vector search alone often underperforms for exact-match queries (product SKUs, names, codes). Production systems typically combine:

  • Vector search for semantic similarity
  • Keyword search (BM25) for exact-term matching
  • Metadata filtering for constraints like date ranges or categories
  • Re-ranking — a second-pass model that reorders top candidates for final relevance

Operational Considerations

  • Index rebuild strategy — how do you handle updates and deletes without full re-indexing?
  • Embedding model versioning — changing embedding models requires re-embedding your entire corpus.
  • Cost at scale — memory-resident indexes get expensive fast; understand your provider's pricing model before committing.
A vector database is only as good as the embeddings feeding it. Invest in embedding quality before optimizing index parameters.
