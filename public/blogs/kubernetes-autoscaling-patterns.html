Kubernetes Autoscaling Patterns for High-Traffic Services

November 12, 2024 · DevOps · 7 min read

Autoscaling is the promise of cloud-native: your service handles a surge in traffic without manual intervention, then scales back down to save cost. In practice, getting autoscaling right on Kubernetes requires understanding the different scaling dimensions and when each applies.

The Three Scaling Dimensions

  1. Horizontal Pod Autoscaler (HPA) — adds or removes pod replicas based on CPU, memory, or custom metrics. The most common starting point.
  2. Vertical Pod Autoscaler (VPA) — adjusts resource requests/limits per pod. Useful for workloads where adding replicas doesn't help (e.g., single-threaded batch jobs).
  3. Cluster Autoscaler — adds or removes nodes when pods can't be scheduled due to insufficient cluster capacity.

Custom Metrics: Beyond CPU

CPU-based autoscaling is a poor proxy for many services. Better signals include:

  • Request queue depth — how many requests are waiting to be processed
  • P99 latency — scale up when latency degrades below SLO threshold
  • Messages in queue — for worker pods consuming from Kafka/SQS
  • Active connections — for WebSocket or long-lived connection services

Use the Prometheus adapter or KEDA (Kubernetes Event-Driven Autoscaler) to feed these custom metrics into HPA decisions.

Scaling for Predictable Traffic

If your traffic is predictable (daily peaks, scheduled events), use scheduled scaling — pre-warm replicas before the spike arrives. Reactive autoscaling alone adds latency because new pods take time to start and warm up.

Anti-Patterns to Avoid

  • Thrashing — scaling up and down rapidly because the metric oscillates. Fix with stabilization windows and cooldown periods.
  • Under-provisioned resource requests — if pods request too little CPU/memory, they get throttled before HPA even triggers. Right-size requests first.
  • Ignoring startup time — if your service takes 60 seconds to start, a sudden spike will cause dropped requests. Use readiness probes and scale ahead of demand.
  • Scaling on average, not tail — average CPU at 50% hides the fact that some pods are saturated. Use max or P95 as the scaling signal.

A Practical Starting Configuration

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-service
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-service
  minReplicas: 3
  maxReplicas: 50
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Percent
          value: 50
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
Autoscaling is not set-and-forget. It requires tuning, load testing, and continuous monitoring — just like the service itself.
